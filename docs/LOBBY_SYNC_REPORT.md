# 참가자별 대기방 동기화·시작 확인 — 2026-09-28

로컬 미리보기의 공유 대기방 객체 직접 조작을 **참가자별 독립 상태 + 신뢰성 제어 메시지**로 바꿨다. 각 참가자가 설정과 준비 상태를 받고, 모두 같은 경기 시작 계획을 확인해야 방장이 첫 라운드를 연다. 실제 EOS 인증·방 검색/입장·인터넷 통신은 아직 없다. 기본 `sdks/eos`와 `config/eos.local.json`이 없는 상태에서 진행한 SDK 독립 연결 작업이다.

## 변경 파일과 동작

- `MultiplayerLobbySession.cs`: 한 참가자의 대기방 제어 채널·상태 복제·준비 응답·시작 확인·경기 연결 수명과 중단 처리를 맡는다. 실제 인증 명단은 연결부가 제공해야 한다.
- `MultiplayerLobbyHost.cs`: 참가자의 마지막 준비 sequence를 상태에 포함하고 시작 계획에 합의한 설정을 고정한다.
- `MultiplayerMatchRuntime.cs`: 대기방에서 합의한 설정이 있으면 첫 라운드 시작 메시지도 그 설정과 일치해야 한다.
- `GalleryProtocol.cs`, `RoundTransport.cs`: 대기방 메시지 allowlist와 대기방용 송수신 패킷 종류를 추가했다. 기존 경기 6종에 대기방 2종을 더한 8종이다.
- `RoundPreviewWindow.Lobby.cs`, `RoundPreviewWindow.xaml.cs`: 역할마다 별도의 세션을 만들고 한 네트워크 루프에서 대기방부터 경기까지 진행한다. 준비 응답 중에는 중복 클릭·시작을 막는다.
- `LobbySessionChecks.cs`, `Program.cs`: 독립 참가자 3명, 패킷/ACK 누락, 준비/시작 경합, 상태 위조·설정 충돌, 이탈·시간 초과와 경기 진입을 검사한다.

준비는 로컬 버튼을 누른 즉시 확정하지 않는다. 방장이 현재 방/revision/인증 송신자/접속 세션/sequence를 검증하고, 그 sequence가 포함된 상태를 돌려줘야 대기가 해제된다. 거절 응답은 해당 요청과 대조하며 예전 응답이 새 요청의 대기를 해제하지 못한다. 설정 revision과 별도로 상태 배포 version을 사용해 준비 변경도 순서대로 적용한다. 상태의 명단·세션·설정·단계·준비 sequence·동일 version 충돌을 검사한다.

시작 과정은 다음과 같다.

1. 방장이 전원 준비를 확인하고 고정된 `LobbyLaunchPlan`을 만든다.
2. 각 참가자는 최신 설정·고정 명단·호환성·자신이 실제 보낸 준비 요청과 계획을 대조한다. 준비 취소가 전송 중이면 계획을 거절한다.
3. 참가자는 대기 상태의 경기 실행기를 만들고 계획 해시가 포함된 수신 확인을 보낸다. 전송 ACK와 이 확인은 별개다.
4. 방장은 전원 확인이 일치한 뒤 자신의 경기 실행기를 열고 첫 라운드를 전달한다. 이전에는 참가자의 작성 타이머·AI 작업을 시작하지 않는다.

계획 해시는 내용 일치 검사이며 서명·변조 방지 보장이 아니다. 중복 시작 정보로 경기 객체를 다시 만들지 않는다. 대기방 연결은 경기 시작 후에도 유지해 늦은 제어 ACK를 처리하며, 경기/이미지 패킷은 최대 256패킷의 별도 수신 큐로 넘긴다. 라운드 교체로 연결을 닫지 않는다.

## 현재 정책과 실제 어댑터의 남은 일

- 대기방 확인 요청 2초/응답 부재 15초, 첫 상태 대기 15초, 전원 시작 정보 확인 30초는 임시값이다. 제어 채널의 10초 전송 제한에 먼저 걸릴 수도 있다. 실패 시 자동 시작하지 않고 중단한다.
- 신뢰성 채널의 32KiB 본문·1,024바이트 패킷·송신 8개/128KiB 제한을 재사용한다. 한 프로세스 전체나 16명 인터넷 성능의 검증값은 아니다.
- 이 동기화 세션은 **하나의 확정된 명단과 접속 세션 ID**에 묶인다. 명단/방장 변경 통지를 받으면 경기까지 중단한다. 이전 `MultiplayerLobbyHost`는 준비 중 명단 갱신을 지원하지만, 새 네트워크 세션에서 참가자를 동적으로 추가하는 처리는 아직 없다.
- 연결부는 입퇴장 후 새 공통 application `LobbyId`와 인증 명단을 확정해 세션을 다시 만들어야 한다. 이는 EOS의 실제 로비 ID를 반드시 바꾸라는 뜻은 아니다. 같은 ID로 신뢰성 채널만 초기화하면 이전 패킷을 구별할 수 없으므로 허용하지 않는다. 이를 온라인 입퇴장/재접속 UI에 연결하는 작업은 남아 있다.
- `ObserveMembership`에는 연결 서비스가 확정한 명단을 전달해야 하며 사용자 메시지의 명단을 신뢰하면 안 된다. 실제 SDK 알림 정리·인증·연결 허용 목록·큐 제어는 아직 구현하지 않았다.
- 클라이언트는 방장 연결만 필요하고 방장은 모든 참가자 연결을 확인한다. 모의 전송의 고정 문자열 ID를 실제 인증으로 설명하지 않는다.
- 중단 시 진행 중 경기/AI를 취소하고 확정된 숫자 결과는 기존 경기 실행기에 보존한다. 재접속·호스트 이전은 지원하지 않는다.

경기 규칙/기존 경기 패킷은 바꾸지 않아 `multiplayer-match-v6`를 유지한다. 이 대기방 프로토콜의 온라인 어댑터 호환성은 SDK 연결 시 함께 검사해야 한다.

## 검증

`lobby-session` 검사에서 다음을 확인했다.

- 독립된 3개 상태의 준비·설정 동기화. 데이터/ACK 첫 전송 누락과 이전 패킷 재주입 후 같은 경기 ID·설정·투표 없는 결과로 종료.
- 한 참가자의 **시작 확인 본문만** 누락하면 패킷 ACK를 받더라도 방장의 경기 객체를 만들지 않는다. 누락을 해제하면 정상 시작한다.
- 준비 취소가 전송 중인 참가자는 시작을 거절하고, 모든 참가자가 중단한다.
- 모델 불일치, 처음부터 방장 메시지 누락, 시작 확인 불가, 연결 상실, 방장/명단 변경 처리.
- 비방장 시작/설정 변경, 가짜 방장 중단 통지, 상태의 준비 요약/동일 revision 설정/동일 version 내용 충돌 거절.
- 방장이 상태 메시지로 로컬 플레이어의 준비 의사를 만들어 내도, 그 플레이어가 직접 준비한 적 없으면 시작 거절.
- 라운드 시작 메시지가 대기방에서 합의한 라운드 수를 바꾸면 거절.

전체 `unit`와 새 `lobby-session` 검사, WPF `lobby-smoke`가 통과했고 Release 빌드는 경고 0/오류 0이다. 전체 검사 후 수신 큐 정리와 추가 시작/설정 검사를 보강하고 해당 검사·빌드를 다시 통과했다. WPF 결과는 `outputs/multiplayer/lobby-session-ui-20260928/`에 보관한다. 이 화면 검사는 AI를 실행하지 않는다.

### 실제 AI·이미지 전송 확인

새 세션 경로로 `round-smoke`를 실행해 **3명 × 1라운드**의 대기방 준비 → 시작 확인 → 번역 수정 → 실제 PNG 생성/전송 → 투표 → 경기 종료를 통과했다. PNG 3장 합계는 **1,174,523바이트**, 득표는 **1/2/0**, 참가자 3명의 기록이 일치했다. 자기 투표 거절도 유지됐다. 원시 결과·프로세스 측정·화면은 `outputs/multiplayer/lobby-session-round-20260928/`에 있다.

| 항목 | 측정 |
|---|---|
| 장치 | GTX 1660 Ti 6GB, 드라이버 591.86 |
| 생성 설정 | 기존 Tiny-SD 혼합 INT8 + TAESD, DirectML, 512×512, 25단계, CFG 7, seed 42/43/44 |
| 번역 | 1.980 / 1.218 / 1.205초 |
| 승인·생성·업로드 | 22.177 / 21.731 / 21.615초 — 순수 추론 시간과 다름 |
| 진단 프로세스 전체 | 78.174초 |
| 최대 working set / private bytes | 1,756,684,288 / 3,622,260,736바이트 |
| 전체 GPU 사용량 | 632~3,796MiB — 다른 앱 포함, 앱 전용 VRAM 아님 |

새 최소 사양이나 생성 품질 개선을 검증한 결과가 아니다. 추가 생성 없이 마지막으로 준비된 상태의 설정 변경 거절을 보강하고 해당 검사·Release 빌드를 다시 확인했다. 실제 여러 PC·EOS·인터넷 이미지 전송은 이 검사에 포함하지 않았다.

## 실행과 다음 작업

```powershell
$env:DOTNET_CLI_HOME = Join-Path (Get-Location) '.cache/dotnet'
$env:NUGET_PACKAGES = Join-Path (Get-Location) '.cache/nuget'
dotnet run --project tests/AIrtist.Checks -c Release --no-restore -- lobby-session .
dotnet build src/AIrtist.App -c Release --no-restore
./scripts/check-app.ps1 -PackageDirectory src/AIrtist.App/bin/Release/net10.0-windows/win-x64 `
  -ModelDirectory models/app-stage3 -OutputDirectory outputs/multiplayer/lobby-session-next -Mode lobby-smoke
```

다음 실제 온라인 작업은 [EOS SDK·개발자 포털 설정 준비](EOS_SETUP.md) 후 기기 ID 인증·실제 방 생성/참가·명단 확정과 P2P를 이 세션에 연결하는 것이다. 서로 다른 PC/회선의 실제 이미지 전송·투표와 깨끗한 PC 검증은 남아 있다. `testbuild` 패키지는 이번에도 갱신하지 않았으며 모델·SDK·중복 패키지를 추가하지 않았다.
