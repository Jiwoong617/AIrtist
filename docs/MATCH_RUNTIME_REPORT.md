# 여러 라운드·결과 기록 연결 — 2026-09-28

같은 날짜의 후속 변경으로 경기 앞에 로컬 대기방 준비/설정·방장 시작을 연결했다. 최신 시작 절차와 검사는 [대기방 보고서](LOBBY_REPORT.md)를 참고한다. 아래 실제 생성 측정은 대기방 추가 전 실행 기록이다.

**경기 미리보기에서 라운드 수를 정하고, 전원이 같은 확정 결과를 받은 뒤 방장이 다음 라운드를 시작하는 흐름을 연결했다.** 새 라운드는 새로운 ID·생성 기회·입력·이미지 상태를 사용하며 이전 라운드의 득표 기록은 보존한다. 마지막 라운드에서는 경기 종료와 전체 라운드 기록을 표시한다.

EOS SDK·로컬 설정이 아직 없어 한 PC의 메모리 내 전송으로 검증했다. 실제 온라인 연결·로비·여러 PC 플레이는 미구현이다. 최종 우승 기준은 미정이므로 현재는 **라운드별 득표 기록만 표시**하며 누적 우승자를 정하지 않는다. `testbuild`는 갱신하지 않았다.

## 변경 파일

- `src/AIrtist.Core/MultiplayerMatchRuntime.cs`: 한 참가자의 전체 경기 수명, 방장 설정/출제, 라운드 교체, 결과 수신 확인, 기록 보존, 이탈·응답 없음에 따른 중단을 구현했다. 경기 설정·제어 계약·스냅샷도 이 파일에 있다.
- `RoundTransport.cs`: 경기 전체 제어용 송수신 종류 두 개를 추가했다. 실제 인증된 송신자 ID를 공급하는 인터페이스는 유지한다.
- `GalleryProtocol.cs`: 경기 시작/다음 라운드·결과 수신 확인·진행 상태·연결 확인 메시지를 기존 제한된 JSON 허용 목록에 추가했다.
- `MultiplayerProtocol.cs`: 현재 호환 규칙을 **`multiplayer-match-v6`**로 변경했다. 기존 v5와 같은 방을 시작할 수 없으며 패킷 버전은 1이다.
- `src/AIrtist.App/RoundPreviewWindow.xaml`, `.xaml.cs`: 라운드 수, 현재/전체 라운드, 방장 전용 다음 라운드, 라운드별 기록과 경기 종료 표시를 연결했다. 기존 역할별 번역 수정과 실제 AI를 재사용한다.
- `App.xaml.cs`, `scripts/check-app.ps1`: 실제 3인 × 2라운드 생성·투표 검사를 수행하는 `--match-smoke`를 추가했다. 기존 `--round-smoke`는 같은 경기 실행기를 1라운드로 검사한다.
- `tests/AIrtist.Checks/MatchRuntimeChecks.cs`, `Program.cs`: 여러 라운드·누락·권한·오래된 메시지·결과 보존·전환 중 늦은 AI·이탈·연결 확인 검사를 추가했다. 전체 `unit`과 별도 `match-runtime`에서 실행한다.
- `AGENTS.md`, `AI_Image_Game_Summary.md`, `README.md`, `APP_DEVELOPMENT.md`, `EOS_SETUP.md`, 이전 실행기 보고서: 최신 상태와 준비/검증 범위를 갱신했다.

## 진행과 보존

경기 전체 제어 채널은 각 상대에 대해 계속 유지한다. 라운드 제어/이미지 채널은 매번 새 ID로 만들고 이전 실행기를 해제한다. 경기 제어의 예약 범위 ID는 MatchId이며 실제 RoundId와 같지 않게 한다. 서로 다른 패킷 종류와 ID 검사를 모두 적용한다. 이미지 큐가 경기를 계속하는 동안 누적되지 않도록 라운드 전송 연결은 실제 연결을 소유하지 않는 수신 큐로 감싼다.

각 참가자는 검증한 확정 결과를 받으면 숫자 기록을 보관하고, **AI 작업 정리까지 끝난 뒤** 결과의 SHA-256을 방장에게 신뢰성 채널로 알린다. 방장은 인증된 참가자·경기·라운드·결과 해시를 자신의 결과와 대조한다. 전원 일치 전에는 다음 라운드를 열지 않는다. 이 해시는 결과 일치 검사이며 서명이나 변조 방지 보장이 아니다.

방장만 현재 RoundId를 지정해 다음 라운드를 시작할 수 있다. 새 시작 메시지는 순서, 이전 결과 해시, 고정 설정·명단·호환성, 제시어 ID를 검사한다. 오래된 번역 확정·취소·투표·다음 라운드 요청도 현재 RoundId와 다르면 거절한다. 상태 revision 역행, 중복/잘못된 수신 확인 명단, 결과 없는 조기 종료와 중단 후 재시작을 거절한다.

각 참가자에게 기록을 보관하므로 마지막 경기 종료나 이후 방장 연결 상실이 기록을 지우지 않는다. 기록에는 라운드 번호·제시어 ID·확정 표 집계만 저장하며 **이전 라운드 PNG/비트맵을 경기 기록에 보관하지 않는다.** 현재 라운드의 그림은 화면에 남기고 다음 라운드/다시 설정/창 닫기 때 해제한다. 앱 종료 후의 파일 저장·복구 기능은 없다.

UI는 경기 실행기 상태를 표시하고 명령만 전달한다. 전환 메시지가 다른 로컬 역할에 도착하는 동안 역할 선택을 잠시 막아 입력 초안이 다른 라운드와 섞이지 않게 했다. 창을 닫거나 다시 설정하면 새로운 경기 ID로 시작한다.

## 임시 정책과 한계

- 라운드 수는 **1~10, 기본 3**이다. 현재 미리보기 인원은 기존 **2~4명**이며 제품 최대/최소 인원 확정은 아니다. Core 참가자 상한은 기존 16명을 유지한다.
- 첫 제시어는 미리보기에서 선택한다. 이후에는 검수한 목록을 섞어 한 번씩 출제하고 목록을 모두 쓰면 다시 섞는다. 목록이 둘 이상이면 주기 경계에서도 바로 같은 단어가 이어지지 않게 한다. AI 출제가 아니다.
- 작성 300초·생성 180초는 기존 미리보기 기본값이며 각 라운드마다 새로 적용한다. 번역·생성 대기 시간도 해당 라운드의 제한 안에 포함한다.
- 전원 결과 수신 확인 기본 제한은 **30초**이고 설정 객체에서 1~120초로 조정할 수 있다. 초과·결과 불일치·라운드 실패·경기 도중 참가자 이탈 시 다음 라운드로 넘어가지 않고 중단한다. 확정된 기록은 보존한다. 미확정 이탈 정책을 대체하는 최종 규칙은 아니다.
- 연결 확인 요청은 기본 **2초**, 참가자의 방장 응답 부재 판정은 **15초**다. 신뢰성 채널의 기존 10초 송신 실패도 중단 조건이다. 단절을 통지하지 않는 로컬 연결에서도 시작/전환 대기가 무한히 남지 않도록 했다. EOS의 실제 연결 상태 감지·재접속·호스트 이전을 구현한 것은 아니다.
- 라운드별 투표 시간·동점·무투표 결과 등은 기존 임시 정책을 유지한다. 누적 점수·공동 우승·재투표는 추가하지 않았다.
- 경기 설정과 미래 단어 순서는 방장에만 존재하며 참가자에게 현재 라운드의 제시어만 전달한다. 번역·생성기는 기존대로 플레이어 묘사만 받는다.

## 검증

### Core

전체 `unit` 검사와 별도 `match-runtime` 검사를 통과했다. 기존 그림그리기·투표·승인·갤러리·신뢰성 전송·한 라운드 검사도 통과했다.

- 모의 AI로 3인 × 2라운드, 총 6번 생성했다. 경기/라운드 제어 데이터·ACK와 이미지 조각 누락 후에도 진행하고 각 라운드가 **1/2/0표**, 전체 기록도 세 참가자에서 일치했다.
- 전원 결과 수신 확인 전에 방장이 진행하려는 요청, 참가자의 진행 요청, 같은 진행 버튼의 중복 요청, 이전 RoundId로 보내는 입력·취소를 거절했다.
- 실제 이전 라운드에서 캡처한 제어/이미지 패킷을 다음 라운드에 다시 넣어도 입력 단계·빈 그림 목록·기존 기록이 바뀌지 않았다.
- 생성 마감 후에도 끝나지 않은 모의 AI 작업이 있으면 결과를 받았더라도 다음 라운드 수신 확인을 보내지 않았다. 늦게 돌아온 PNG를 폐기하고 정리 후 진행했으며 새 라운드에는 이미지/초안이 없었다.
- 결과 확인 메시지를 막았다가 복구하면 그동안 진행할 수 없고 재전송 후 진행할 수 있었다. 완전히 끊긴 참가자, 시작 메시지를 받지 못하는 참가자는 중단 상태에 도달했다.
- 결과 확인 제한을 1초로 설정하고 한 명의 응답을 막으면 기록을 유지한 채 중단했다. 패킷 자체의 해시는 유효하지만 다른 결과 해시를 주장하는 참가자도 검사해, 결과 불일치로 전원이 중단하고 다음 라운드를 열지 않는 것을 확인했다.
- 두 라운드 모두 그림이 없으면 두 번의 무투표 결과를 보존하고 경기 종료했다. 마지막 라운드 이후에는 더 진행할 수 없었다.
- 잘못된 초기 설정/수신자/제시어, 건너뛴 라운드, 결과 없는 다음 라운드, 같은 revision의 충돌, 낮은 revision, 중복 준비 ID, 다른 참가자가 위조한 종료, 중단 뒤 재시작을 거절했다.

## 실행 방법과 다음 작업

```powershell
$env:DOTNET_CLI_HOME = Join-Path (Get-Location) '.cache/dotnet'
$env:NUGET_PACKAGES = Join-Path (Get-Location) '.cache/nuget'
dotnet run --project tests/AIrtist.Checks -c Release --no-restore -- unit .
dotnet build src/AIrtist.App -c Release --no-restore
& ./src/AIrtist.App/bin/Release/net10.0-windows/win-x64/AIrtist.exe --models D:/AIrtist/models/app-stage3

# 새 출력 폴더를 사용한다. 실제 생성 6회가 실행된다.
./scripts/check-app.ps1 -PackageDirectory src/AIrtist.App/bin/Release/net10.0-windows/win-x64 `
  -ModelDirectory models/app-stage3 -OutputDirectory outputs/multiplayer/match-runtime-next -Mode match-smoke
```

다음은 [EOS C# SDK·설정 준비](EOS_SETUP.md) 후 기기 ID 인증, 방 생성/참가, 호환성 검사와 실제 P2P 전송을 연결하는 작업이다. 전송 어댑터는 경기 수명 동안 연결을 유지하고 SDK가 인증한 송신자 ID를 Core에 전달해야 한다. 이후 다른 회선의 PC에서 3인 이상 경기 완주·실패/이탈을 검증한다. 최종 우승 기준·재접속/호스트 이전·저사양/깨끗한 PC·최종 배포 용량 검증도 남아 있다.

기존 `testbuild`는 **922,301,469바이트 / 439개 파일**의 과거 패키지 그대로다. 최신 소스는 개발 빌드 경로와 로컬 모델 지정으로 실행한다. 이번에 모델·SDK·의존성을 추가하거나 패키지를 중복 생성하지 않았고, 진단 결과와 빌드 출력은 기존 Git 제외 규칙을 적용한다. 커밋/푸시는 수행하지 않았다.
