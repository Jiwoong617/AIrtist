# 이미지 누락 복구·완료 확인·생성 실패 통지 — 2026-09-27

이 문서는 v4 단계 기록이다. 같은 날 진행한 실행기·로컬 AI·경기 미리보기 연결과 v5 검사는 [후속 보고서](ROUND_RUNTIME_REPORT.md)를 참고한다.

업로드와 갤러리 배포에 **누락 조각만 재전송하는 송신 대기열**을 연결했다. 수신자는 검증한 조각 목록을 제어 메시지로 돌려주며, 전체 해시와 PNG 검증이 끝나야 완료를 알린다. 생성 실패도 승인 ID를 대조해 호스트에 통지한다. **SDK 독립적인 코드와 메모리 내 검사이며 실제 EOS 접속·온라인 UI·AI 실행 연결은 아직 아니다.**

## 변경 파일

- `src/AIrtist.Core/ReliableImageSendQueue.cs`: 이미지 송신·조각 수신 현황 요청/응답, 누락 재전송, 완료/실패 이벤트, 공통 속도·메모리·대기열·마감 제한을 추가했다.
- `MultiplayerProtocol.cs`: 특정 이미지 조각을 만드는 공통 함수와 수신 조각 비트맵을 추가했다. 기존 1,024바이트 이미지 패킷 형식은 유지하며 새 흐름의 규칙 버전은 **`multiplayer-round-v4`**다.
- `MultiplayerRoundHost.cs`, `MultiplayerRoundClient.cs`: 승인된 전송/갤러리의 수신 현황과 검증 완료를 응답한다. 상태 문의만으로 이미지 버퍼를 만들지 않는다.
- `RoundControlDispatch.cs`, `GalleryProtocol.cs`: 수신 현황·완료 응답·생성 실패/응답을 기존 신뢰성 제어 전송에 연결했다. 호스트는 갤러리의 모든 수신자에 하나의 이미지 송신 예산을 공유한다.
- `MultiplayerSubmissionClient.cs`: 전송 허가 후 큐 등록, 완료/실패에 따른 버퍼 해제·상태 전환, 생성 실패 통지를 연결했다. 완료 응답보다 갤러리가 먼저 와도 자신의 승인 ID·소유자·길이·해시가 일치하면 업로드 완료로 처리한다.
- `tests/AIrtist.Checks/ImageSendChecks.cs`, `RoundDispatchChecks.cs`, `Program.cs`: 조각별 재전송·상한·속도·마감·실패 검사와 `image-recovery` 통합 진단을 추가했다.

## 전송 처리와 임시 상한

| 항목 | 현재 값/동작 |
|---|---|
| 이미지 한 장 | 기존 최대 4MiB, PNG 가로·세로 최대 1,024픽셀 |
| 이미지 패킷 | 최대 1,024바이트, 본문 992바이트 |
| 수신 조각 비트맵 | 최대 4,229조각 / 529바이트, 제어 메시지 안에서 전송 |
| 송신 대기열 | 송신 중 항목과 미소비 결과 합계 최대 16개 |
| 송신 PNG 보관 | 로컬 라운드의 이미지 송신 큐당 최대 16MiB |
| 중복 방지 기록 | 상대·전송 ID 조합 최대 256개/라운드 |
| 기본 이미지 속도 | 큐 전체 초당 1,024패킷, 즉시 전송 여유 최대 32패킷 |
| 공평한 전송 | 보낼 조각이 있는 항목을 순환하며 한 조각씩 배정 |
| 수신 현황 문의 | 한 전송당 응답 대기 중인 문의 하나, 기본 최소 간격 500ms |
| 문의 큐 등록 | 호출당 최대 4개, 제어 송신 큐가 가득 차면 다음 호출에서 재시도 |

속도와 문의 간격은 `ImageSendPolicy`의 임시 기본값이며 실제 인터넷 처리량을 측정한 값이 아니다. 이미지 데이터 속도와 제어 메시지 속도는 별도다. 16명·최대 크기 그림들을 기본 마감 안에 배포할 수 있음을 검증한 것으로 해석하지 않는다.

한 차례 필요한 조각을 보낸 뒤 `ImageProgressRequest`를 신뢰성 제어 채널에 등록한다. 응답의 인증된 상대·수신자·경기/라운드·승인/전송 ID·버전·문의 ID를 확인하고, 비트맵의 길이·사용하지 않는 비트·이미 확인된 조각의 역행을 검사한다. 빠진 조각만 다음 전송에 예약한다. 문의/응답 패킷 누락은 기존 제어 채널이 복구하므로 동시에 여러 문의를 쌓지 않는다.

`Receiving`에 모든 조각이 있다고 주장하는 응답만으로는 완료하지 않는다. 수신 Core가 해시와 실제 PNG 디코딩을 통과한 뒤 `Complete`를 반환해야 한다. 형식이 잘못된 PNG는 해시가 맞아도 거절한다. 이미 완료한 그림에 대한 문의 재전송은 같은 완료 상태를 돌려주며, 송신 측은 완료 이벤트를 한 번만 꺼낸다. 이는 연결 상대를 신뢰하는 친구 간 검증이며 악성 참가자가 실제 그림을 봤다는 증명은 아니다.

업로드 송신 마감은 큐 등록 시 생성 잔여 시간과 전송 제한 중 짧은 값, 갤러리는 호스트의 갤러리 잔여 시간을 사용한다. 재시도·응답으로 마감을 연장하지 않는다. 수신 Core의 기존 절대 마감도 유지한다. 완료·거절·마감·취소·이탈 시 송신 PNG를 해제한다. 보관 상한은 송신 복사본 기준이며 원본·수신 버퍼·디코딩 비트맵·임시 복사·SDK 큐를 합친 프로세스 메모리 상한이 아니다.

`GenerationFailedMessage`는 현재 경기/라운드·인증된 참가자·승인 ID에만 적용한다. 호스트는 수신 중 버퍼와 예약량을 해제하고 기존 생성권은 소비된 상태로 둔다. 재전송은 새 생성권을 만들지 않는다. 응답 대기는 기존 임시 10초를 사용하며 늦은 응답은 생성·송신을 재개하지 않는다.

## 어댑터 연결 방법

클라이언트는 전송 허가 후 `QueueImage`를 호출하고 `PollImagePackets`, `PumpImageProgress`를 네트워크 루프에서 실행한다. 호스트는 `HostControlDispatcher.QueueGalleryImage`에 갤러리 항목을 등록한 뒤 **하나의** `Images` 큐를 순환시킨다. 큐가 가득 차면 해당 항목 등록을 보류하고, `TakeResults`로 완료/실패를 소비한다. 직접 모든 조각을 한꺼번에 큐에 넣지 않는다. 기존 `UploadPackets`/`GalleryPackets`는 원시 분할 API이며 새 어댑터의 복구·속도 제한 경로를 대신하지 않는다.

`PumpProgressRequests`/`PumpImageProgress`의 콜백은 해당 상대의 `ReliableControlEndpoint.Queue`에 메시지를 등록하고 상태를 반환해야 한다. 문의는 그 상대의 인증된 연결로 보내며 응답은 기존 호스트/참가자 dispatcher가 처리한다. 생성 작업 실패·취소 시 현재 승인 ID로 `CreateGenerationFailure`를 만들고 같은 제어 채널로 보낸다.

호스트 dispatcher와 이미지 송신 큐는 단일 네트워크 루프에서 접근하고 라운드 종료 시 해제한다. 연결이 끊긴 상대는 송신 큐의 `DisconnectPeer`로 정리한다. SDK의 송신 실패는 패킷 누락으로 취급하고 다음 수신 현황으로 복구한다. 실제 SDK 송신/수신 큐의 한도와 여러 라운드의 수명·상태 배포는 어댑터에서 연결해야 한다.

## 수행한 검사

.NET SDK **10.0.103**에서 전체 `unit`과 `image-recovery`를 통과했다. WPF Release 빌드는 **경고 0 / 오류 0**이다.

- 새 송신 검사: 여러 수신자가 동일 속도 예산을 공유함, 공평한 조각 배정, 즉시 전송·시간 경과 후 보충 한도, 이미 받은 조각을 제외한 재전송을 확인했다.
- 잘못된 상대/수신자/라운드/승인·문의 ID, 비트맵 길이·남는 비트·역행·중복 응답을 거절했다. 해시가 맞아도 PNG가 아니면 완료 응답을 만들지 않았다.
- 16MiB·16개·256개 기록 상한과 미소비 완료 이벤트 상한을 검사했다. 정확한 마감, 마감 직전 수신 현황에도 타이머 연장 없음, 취소/이탈/종료 후 버퍼 해제를 확인했다.
- 생성 실패 메시지와 ACK를 누락·재전송해도 실패 상태가 한 번 반영되고 재생성되지 않았다. 수신 중 이미지 버퍼/예약도 해제됐다. 갤러리가 업로드 완료 응답을 앞질러도 성공을 취소로 표시하지 않았다.
- 모의 참가자 3개(호스트 화면 포함)가 시작 → 승인 → 업로드 → 갤러리 → 투표 결과를 완주했다. 기존 실제 PNG 3장 합계 **891,234바이트**를 재사용했으며 실제 AI는 실행하지 않았다.
- **이미지 패킷 216개**(각 전송의 17번째 간격 조각을 최초 한 번 누락), **제어 패킷 174개**(문의·응답을 포함해 첫 데이터/ACK 누락)를 빠뜨리고 역순·중복도 적용했다. 업로드 **3건 + 갤러리 9건 = 12건**의 완료를 확인했다. 모든 참가자의 결과가 **1/2/0표**로 일치했고 송신 PNG 버퍼는 비워졌다.
- 생성한 이미지 패킷은 업로드 **954개**, 갤러리 **2,862개**다. 원본 조각 900개/2,700개에 누락분 54개/162개만 추가 전송했다. 제어 패킷은 **465개**다. 이 개수에는 의도적으로 누락한 패킷을 포함하며 중복 전달하는 검사 호출은 별도다.
- `scripts/check-eos-setup.ps1`은 설정 부재로 종료 코드 **2**다.

원시 결과는 Git 제외 경로 `outputs/multiplayer/image-recovery-round-check.json`에 있다. 검사 입력은 `outputs/scoring-removal/packaged-drawing/`의 기존 `generated.png`, `generated-repeat.png`, `generated-revised.png`다. 새 복제본에서는 `unit`이 작은 PNG를 자체 구성하며, 실제 이미지 진단에는 해당 로컬 파일을 준비해야 한다.

```powershell
$env:DOTNET_CLI_HOME = Join-Path (Get-Location) '.cache/dotnet'
$env:NUGET_PACKAGES = Join-Path (Get-Location) '.cache/nuget'
dotnet run --project tests/AIrtist.Checks -c Release --no-restore -- unit .
dotnet run --project tests/AIrtist.Checks -c Release --no-build --no-restore -- image-recovery .
```
