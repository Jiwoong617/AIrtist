> **2026-10-04 후속:** 아래는 수정 전의 기준 측정이다. 공급자 재사용·GPU 취소 방식 수정 후 실제 30장과 취소/시간 초과 각 3회 복구가 통과했고, 핸들의 기존 누적 증가 양상을 재현하지 않았다. 30장 PNG 해시는 기준 측정과 모두 같았다. [최신 수정·검증과 남은 제약](GPU_RESOURCE_FIX_REPORT.md)

EOS 포털 설정 5개가 아직 비어 있어 서비스 검증과 독립적인 로컬 AI 반복 검사를 진행했다. 앱 기능·모델·`testbuild`를 변경하지 않고 개발용 검사 도구를 확장했다.

## 변경 파일과 검사 방법

- `tests/AIrtist.Checks/DrawingSoak.cs`: 같은 프로세스에서 `DrawingController` → `SerializedDrawingAi` → 실제 번역/생성기로 반복한다.
- `tests/AIrtist.Checks/DrawingResourceProbe.cs`: 추론·컨트롤러·PNG 없이 모델 세션 생성/해제 구간의 자원 증가를 분리한다.
- `tests/AIrtist.Checks/Program.cs`: `soak` 실행 모드, 완료 장수·출력 경로 인자.
- `scripts/check-drawing-soak.ps1`: 숨겨진 검사 EXE 실행, GPU 전체 표본·실제 런타임 경로·로그 기록, 제한 시간 후 자기 진단 프로세스만 종료.
- 기존 짧은 `stability` 명령과 제품 코드는 그대로 유지했다. 진단 코드의 Release 빌드는 경고/오류 0개, 전체 Core 규칙 검사와 잘못된 장수/기존 결과 덮어쓰기 거절 검사를 통과했다.

```powershell
$env:DOTNET_CLI_HOME = Join-Path (Get-Location) '.cache/dotnet'
$env:NUGET_PACKAGES = Join-Path (Get-Location) '.cache/nuget'
dotnet build tests/AIrtist.Checks -c Release --no-restore
.\scripts\check-drawing-soak.ps1 -OutputDirectory outputs/drawing-soak/run-new -Images 30 -MaxMinutes 30
```

기본 30장, 10장마다 취소와 10초 제한 시간 초과를 각 1회 유도한다. 취소는 세 번째 U-Net 단계 진입 시 요청한다. 취소 전 그림 보존과 완료 후 작업 가능 상태를 검사하고 이어서 실제 그림을 생성한다. 제한 시간 초과는 동일 AI를 쓰는 별도 10초 컨트롤러로 검사하며 복구 생성은 기본 180초 컨트롤러에서 수행한다. 같은 제한 시간 컨트롤러를 재설정해 회복한 검사로 설명하지 않는다.

6종은 토끼·사과·자동차·집·상하 관계의 공/상자·배다. 2회마다 새 원문을 번역하고 미리 작성한 동일 의미의 영어로 확정해 생성한다. 각 쌍의 두 번째 생성은 번역을 반복하지 않고 같은 초안과 다른 시드를 사용한다. 번역 원문/자동 결과/확정문, PNG 해시·크기와 복원 가능한 512×512 여부를 기록한다. 의미 정확도 자동 판정은 없다.

30장 실행에서는 첫 6종의 대표 이미지와 마지막 2장, 총 8장만 저장한다. 보고서 행에는 PNG 바이트를 보관하지 않는다. 작업 중 강제 GC를 호출하지 않으며 약 100ms마다 메모리 표본, 작업 직후 메모리·핸들·스레드 수를 기록한다. 10월 3일 후속에는 모든 작업 종료 후 컨트롤러 해제·2초 대기·진단용 GC 후의 수치를 추가했다. 마지막 GC는 제품 동작이나 반복 구간의 메모리 개선에 사용하지 않는다.

## 후속 작업 — GPU 세션 구간 분리

같은 apphost와 DLL로 추론을 전혀 실행하지 않고 CPU 번역·GPU 텍스트/U-Net/디코더 세션을 각각 4회 열고 닫았다. 매번 `Dispose` 후 진단용 GC까지 수행했다. 컨트롤러·입력 토큰·이미지 인코딩/복원은 실행하지 않았다.

```powershell
.\tests\AIrtist.Checks\bin\Release\net10.0-windows\AIrtist.Checks.exe resource-probe . outputs/drawing-resource/run-new
```

원자료: `outputs/drawing-resource/20261003-sessions/results.json`. 상태는 `recorded`이며 누수 없음 판정이 아니다. 실제 로드한 ORT/DirectML의 경로와 해시는 위 배포 구성과 일치한다.

| 세션 | 4회 각각 해제+GC 후 핸들 수 |
|---|---|
| CPU 번역 | 258 → 260 → 260 → 260 |
| GPU 텍스트 | 333 → 335 → 337 → 339 |
| GPU U-Net | 341 → 343 → 347 → 349 |
| GPU 디코더 | 351 → 353 → 355 → 357 |

초기 준비 이후 CPU 번역은 일정했고 GPU 세션은 대부분 회당 2개 증가했다. **증가 구간을 GPU 세션 생성/해제로 좁혔지만, ORT·DirectML·드라이버 중 정확한 소유자나 원인을 확정한 것은 아니다.** 제품 세션은 이미 `using`으로 해제한다. 이번에는 강제 GC를 제품에 넣거나 확인되지 않은 런타임 교체·세션 캐시를 적용하지 않았다. 다음은 이 최소 재현을 기준으로 원인을 확인하고 수정 후보의 자원·품질·속도·배포 용량을 비교하는 작업이다.

## 대표 이미지 확인

첫 실행의 6종 대표 PNG를 직접 확인했고 후속 파일과 해시가 일치했다. 흰 토끼/긴 귀, 빨간 사과/파란 배경, 노란 집/파란 지붕/초록 지형, 흰 배/파란 물은 확인할 수 있다. 자동차는 확대되어 잘렸고 바퀴 네 개를 확인할 수 없었다. 공/상자 묘사는 파란 상자만 뚜렷하고 빨간 공과 상하 관계를 재현하지 못했다. 생성 성공과 의미·개수·관계의 품질 합격을 구분한다. 자동 번역 정확도 개선 작업도 아니다.

## 해석과 남은 검사

이 검사는 현재 개발 PC의 Core·실제 AI 반복 실행이다. `testbuild` EXE의 WPF 화면을 장시간 조작한 검사나 패키지 재배포 검사가 아니다. 기존 실행 폴더는 943,403,670바이트 / 444개 파일을 유지한다.

private bytes는 실제 상주 RAM과 다르며 작업마다 GC 시점에 따라 달라진다. 이 제한된 실행으로 메모리 누수가 없다고 보장하지 않는다. GPU 값은 약 2초 간격의 다른 앱을 포함한 전체 표본이며 앱 전용 VRAM이나 4GB 최소 사양의 근거가 아니다.

`FirstStepSeconds`는 생성 시작부터 첫 U-Net 단계 진입까지로 토큰 처리·텍스트 인코딩·세션 준비 등이 포함된다. `DecodeStartSeconds`는 디코더 시작 직전까지의 누적 시간이다. 순수 모델 로딩이나 GPU 추론 시간으로 해석하지 않는다. 첫 실행 초기에는 Core 규칙 검사도 잠시 겹쳤고 런타임 차이도 있으므로 과거 대비 속도 개선 주장에 사용하지 않는다.

여러 시간에 걸친 WPF 사용, 별도 4GB VRAM/16GB RAM PC, 실제 한국어 IME·모니터 DPI 전환, 개발 도구 없는 Windows와 네트워크 차단 상태의 최초 실행은 남아 있다. 실제 EOS 인증·다른 회선 2PC 이미지 전송·3인 투표는 포털 설정과 별도 기기가 준비된 뒤 검사한다.
