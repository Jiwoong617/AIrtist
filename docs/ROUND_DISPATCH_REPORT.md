# 경기 시작·제출 승인 메시지 연결 — 2026-09-27

후속 작업: 같은 날 이미지 누락 조각 재전송·공통 송신량 제한·완료 확인·생성 실패 통지를 연결했다. 아래는 규칙 v3 단계 기록이며 최신 v4 구현과 검사는 [이미지 복구 보고서](IMAGE_RECOVERY_REPORT.md)를 따른다.

한 라운드의 **시작 → 묘사 확정 → 생성 승인 → 이미지 전송 허가 → 갤러리 → 투표/결과**를 제어 메시지 분배에 연결했다. 제어 패킷을 누락·중복시켜도 생성 승인을 참가자당 한 번만 꺼낼 수 있으며 세 참가자의 결과가 일치했다. **메모리 내 모의 연결 검사이고 EOS 접속·온라인 UI·실제 AI 호출 연결은 아직 아니다.**

## 변경 파일

- `src/AIrtist.Core/RoundControlDispatch.cs`: 시작·승인 응답·이미지 전송 허가 계약, `HostControlDispatcher`, `ReliableControlEndpoint`를 추가했다. 방장은 인증된 송신자와 경기/라운드/상태 버전을 확인해 기존 Core 규칙을 호출한다. 참가자가 보낸 호스트 전용 메시지를 거절한다.
- `src/AIrtist.Core/MultiplayerSubmissionClient.cs`: 시작·제출 대기·생성 승인·전송 허가 상태를 관리하고 기존 `MultiplayerRoundClient`의 갤러리/투표 처리를 소유한다. 실제 번역·생성 실행 객체나 UI는 호출하지 않는다.
- `MultiplayerRoundHost.cs`: 수신자별 시작 메시지와 요청 ID를 포함한 제출 응답을 만든다. 응답의 생성 잔여 시간은 방장의 단조 시계와 실제 참가자 상태를 기준으로 한다.
- `GalleryProtocol.cs`: 기존 코덱에 시작/제출/응답/이미지 전송 시작 종류와 허용 목록 기반 분배용 디코딩을 추가했다. 필요한 생성자 필드가 빠진 JSON도 거절한다. 최대 32KiB·깊이 16·알 수 없는 필드 거절은 유지한다.
- `MultiplayerProtocol.cs`: 새 시작/응답 흐름을 구형 앱과 구분하도록 규칙 버전을 **`multiplayer-round-v3`**로 올렸다. 패킷·제어 봉투의 통신 버전은 1 그대로다.
- `tests/AIrtist.Checks/RoundDispatchChecks.cs`, `Program.cs`: 전체 `unit`에 새 검사를 포함하고 기존 실제 PNG를 사용하는 `round-dispatch` 명령을 추가했다.

## 동작과 경계

시작 메시지에는 제시어의 ID·표시명·뜻, 고정 참가자, 호환성, 제한 시간이 있다. 참가자는 이를 로비에서 확정한 방장·명단·호환성과 검증된 로컬 단어 목록에 대조한다. 새 네트워크 참가자를 메시지 자체로 등록하지 않는다. 시작 재전송은 작성 시간을 늘리거나 상태를 초기화하지 않는다.

번역 준비·수정은 제출을 만들지 않는다. 최종 확정 때 `CreateSubmission`을 호출하고 동일 요청 재시도는 같은 요청 ID와 문장을 유지한다. 승인 응답의 요청·수신자·라운드·승인 ID·묘사·번역을 확인한 뒤 `TakeGenerationApproval`에서 **한 번만** 생성 입력을 반환한다. 이 입력에는 제시어가 없다. 같은 승인이나 제출을 다시 보내도 새 생성 입력이 나오지 않는다. 실제 생성기 호출은 이후 어댑터의 책임이다.

잘못된 입력에 대한 거절은 남은 작성 시간 안에 재작성할 수 있게 한다. 새 요청 이후 도착한 이전 거절은 무시한다. 승인 응답·이미지 전송 허가의 대기 상한은 임시 **10초**다. 마감 이후 도착한 응답은 작업을 재개하지 않는다. 생성 잔여 시간은 첫 승인 수신 때 요청 후 대기한 시간을 보수적으로 차감한다. PC 간 시계 일치를 가정하지 않으며 재전송으로 시간을 늘리지 않는다. 실제 생성/제출 마감은 계속 방장이 판정한다.

`PrepareImage`는 전송 정보를 만들고 허가를 기다린다. `UploadPackets`는 방장의 유효한 `Accepted`/`Duplicate` 응답 후에만 바이트를 제공한다. 거절·시간 초과·갤러리 전환·연결 종료 후에는 허용하지 않는다. PNG는 기존 분할·크기·해시·디코딩 검사를 거치며 **이미지 패킷 누락 재전송은 이번 범위에 포함하지 않았다.**

`ReliableControlEndpoint`는 기존 채널을 메시지 분배에 연결한다. 송신 대기열이 가득 차면 응답 하나(최대 32KiB)를 보류하고, 해당 응답을 대기열에 넣은 뒤 수신 요청을 ACK한다. 재시도 중 핸들러를 다시 호출하지 않으며 마감·종료 시 보류 응답을 해제한다. 기존 송신 대기열 8개/128KiB 외에 이 응답 버퍼가 추가될 수 있다. ACK는 처리와 응답 등록을 뜻하며 게임 승인 여부나 응답의 상대 수신 완료를 뜻하지 않는다.

어댑터는 상대·라운드별 endpoint를 유지하고 단일 네트워크 루프에서 접근을 직렬화해야 한다. `Queue`가 가득 차면 호출자도 무제한 메시지를 쌓지 않는다. 인증된 SDK 송신자를 `Receive`에 넘기고 `PollPackets`를 주기적으로 전송한다. 실패 시 UI·클라이언트 상태에 연결 종료를 전달한다. 새 갤러리·투표 상태의 전원 배포 시점과 실제 이미지 전송 루프는 경기 어댑터가 담당한다. 같은 라운드 ID로 endpoint만 재생성하는 재접속은 지원하지 않는다.

## 검증 결과

.NET SDK **10.0.103**, 개발 PC에서 다음을 실행했다.

- 전체 `unit` 통과: 기존 그림그리기·자산·투표·갤러리·제어 전송 회귀 검사와 새 시작/제출/응답 검사를 포함한다.
- 호스트 사칭·다른 수신자·이전 라운드/버전·호환성 불일치·바뀐 제시어/명단/정책·잘못된 메시지 방향·크기/필드 누락·알 수 없는 종류를 거절했다.
- 잘못된 입력은 생성권을 쓰지 않으며, 중복 제출/승인·동시 승인 꺼내기 12회에서도 생성 입력은 한 번만 반환했다. 잘못된 요청 ID·수정된 승인 문장·교체된 승인 ID·전송 ID를 거절했다.
- 시작/승인 재전송이 타이머를 늘리지 않음, 승인/전송 허가 응답의 10초 마감, 이동 중 만료된 생성 예산, 종료 후 늦은 응답 거절을 확인했다.
- 송신 대기열 8개가 찬 상태에서 응답을 보류했다가 전송해 핸들러 한 번·응답 한 번을 확인했다. 계속 막히면 마감 후 버퍼가 해제됐다.
- `round-dispatch`: 독립 클라이언트 3개(호스트 화면 포함), 지속되는 양방향 endpoint로 라운드를 완주했다. 제어 패킷 **225개 생성 중 78개**를 의도적으로 누락했고 중복·역순 전달도 적용했다. 생성 승인 꺼내기는 **총 3회**, 결과는 모두 **1/2/0표**다. 숫자 225에는 의도적으로 누락한 패킷을 포함한다.
- 기존 실제 PNG 3장 **891,234바이트 / 업로드 900개 이미지 패킷**, 참가자 3개 갤러리에 총 **2,700개 이미지 패킷**을 전달했다. 이미지 패킷에는 역순·중복만 적용했으며 누락 복구 검사는 아니다. 실제 생성기를 실행하지 않았다.
- WPF Release 빌드 **경고 0 / 오류 0**. EOS 준비 스크립트는 로컬 설정 부재로 종료 코드 **2**다.

원시 결과: `outputs/multiplayer/round-dispatch-check.json`(Git 제외). 이미지 입력은 기존 `outputs/scoring-removal/packaged-drawing/generated.png`, `generated-repeat.png`, `generated-revised.png`다. 이 파일이 없는 복제본에서는 `unit`의 작은 PNG 픽스처로 규칙을 검사할 수 있다.
