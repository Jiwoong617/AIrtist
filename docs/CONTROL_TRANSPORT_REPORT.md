# 제어 메시지 분할·재전송·수신 확인 — 2026-09-26

후속 작업: 2026-09-27 시작·제출 승인·이미지 전송 허가의 직렬화/분배와 응답 대기열 연결을 구현했다. 아래는 9월 26일 기록이며 최신 상태는 [경기 메시지 연결 보고서](ROUND_DISPATCH_REPORT.md)를 따른다.

멀티플레이 4번 작업 중 SDK 독립적인 제어 메시지 전송을 구현했다. 갤러리 목록·수신 완료·투표 시작·투표 요청·확정 결과를 작은 패킷으로 나누고, 누락 시 재전송하며 같은 메시지를 한 번만 처리한다. **실제 EOS SDK·설정은 아직 없으며 온라인 방에 연결하는 기능은 구현 전**이다. 이번 변경은 Core와 검사 코드이며 기존 `testbuild`를 교체하지 않았다.

## 변경 파일과 동작

- `src/AIrtist.Core/ReliableControlChannel.cs`: 한 라운드의 인증된 상대 한 명과 사용하는 양방향 채널. 순번·경기/라운드·길이·SHA-256을 검사하고 분할·재조립·ACK·재전송·송신 대기열·속도·시간 제한을 관리한다. 자체 인증이나 소켓 연결은 하지 않는다.
- `tests/AIrtist.Checks/ControlTransportChecks.cs`: 패킷/ACK 누락, 순서 변경·중복, 위조·손상·상한·마감 검사를 추가했다. 별도 `control-loopback` 명령은 실제 OS UDP 소켓 두 개를 `127.0.0.1`에 열어 전송한다.
- `tests/AIrtist.Checks/GallerySyncChecks.cs`: 참가자별로 유지되는 채널을 통해 갤러리·준비 확인·투표/결과를 적용하는 통합 검사를 추가했다. 이미지 바이트 전송은 기존 이미지 패킷을 사용한다.
- `tests/AIrtist.Checks/Program.cs`: `unit`에 제어 전송 검사를 포함하고 `reliable-gallery`, `control-loopback` 진단 명령을 추가했다.

게임 규칙은 `multiplayer-round-v2` 그대로다. 새 제어 패킷은 `CTL1` 식별자/통신 버전 1을 사용하며 기존 이미지 패킷과 구분한다. ACK는 해당 메시지의 처리 완료를 뜻한다. 제출 승인이나 유효 표 인정 여부는 별도 게임 응답으로 판단해야 한다.

## 상한과 임시 전송 정책

| 항목 | 현재 값 |
|---|---|
| 제어 메시지 | 최대 32KiB |
| 한 패킷 | 최대 1,024바이트: 헤더 88 + 본문 최대 936 |
| 메시지당 분할 수 | 최대 36개 |
| 상대별 송신 대기열 | 진행 중 메시지 포함 최대 8개, 본문 합계 128KiB |
| 상대별 수신 | 한 번에 한 메시지, 본문 최대 32KiB |
| 기본 속도 | ACK 포함 초당 64패킷, 즉시 전송 여유 최대 8패킷 |
| 기본 재시도 | 한 차례의 분할 전송을 마친 뒤 ACK가 없으면 500ms 후 같은 순번 재전송 |
| 기본 마감 | 송신 대기열 등록/첫 조각 수신부터 각각 10초 |

정책은 `ControlChannelPolicy`로 변경한다. 기본값은 실제 회선 성능을 측정해 확정한 제품 정책이 아니다. 수신 마감에는 애플리케이션 처리 시간도 포함하며 중복 패킷으로 연장하지 않는다. ACK가 와야 다음 송신 메시지로 넘어가므로 순서가 보장된다. ACK가 유실되면 직전 순번을 다시 확인해 ACK만 재전송하고 게임 처리를 반복하지 않는다.

상대 ID·경기/라운드·헤더·조각 길이/수 등을 검사한 뒤 본문 버퍼를 할당한다. 같은 조각의 내용 충돌이나 완성 본문의 SHA 불일치, 마감·연결 종료 시 채널을 닫고 대기 중 버퍼를 해제한다. 이미 소비한 본문의 복사본, SDK 큐와 소켓·이미지·UI 메모리를 포함한 프로세스 전체 상한은 아니다. SHA 검사는 손상 검출이며 인증·변조 방지 보장이 아니다.

## 어댑터 연결 계약

1. 로비가 확정한 경기/라운드와 인증된 상대마다 채널 하나를 유지한다. 외부 메시지의 PlayerId 대신 SDK가 확인한 송신자를 `Receive`에 넘긴다. 같은 라운드 ID로 채널만 재생성하면 순번 기록이 초기화되므로 재접속 방식으로 사용하지 않는다.
2. `TryQueue`의 `Backpressure`를 처리하고 어댑터 바깥에 무제한 대기열을 만들지 않는다. `PollPackets`를 주기적으로 호출해 반환한 패킷을 바로 보낸다. SDK 송신 실패는 패킷 누락으로 취급해 기존 순번이 재시도하도록 하며 새 메시지로 다시 등록하지 않는다.
3. `TakeReceived`로 얻은 본문을 한 번만 디코딩·분배한다. 게임 처리를 적용했거나 의도적으로 거절한 뒤 `ConfirmReceived`를 호출한다. 이를 호출하기 전에는 ACK를 보내지 않는다. 처리 예외는 어댑터의 실패 처리로 연결해야 한다.
4. `Snapshot` 등의 마감 판정을 확인하고 실패를 경기/UI에 전달한다. 검사에서는 확정 결과 수신 후 전송 마감을 발생시키고 `MarkHostUnavailable`을 호출해 결과 보존을 확인했다. 실제 이탈 감지와 자동 호출은 아직 없다.
5. 라운드 종료·연결 종료 시 채널을 정리한다. 새 라운드에는 새 컨텍스트를 사용한다. 실제 SDK의 패킷 상한·송신 방식·수신 큐와 참가자 전체의 전송량을 확인하고 이미지 패킷과 별도로 라우팅해야 한다.

현재 통합 검사는 갤러리 이후의 기존 제어 메시지 코덱을 사용한다. 제출 요청/승인·라운드 시작 계약의 직렬화와 실제 메시지 종류별 분배, 이미지 송신 재시도·속도 조절은 후속 작업이다. 이 클래스가 이미지 전체의 안정적인 전송이나 EOS 연결을 구현한 것으로 취급하지 않는다.

## 수행한 검사

개발 PC의 .NET SDK **10.0.103**에서 다음 검사를 통과했다.

- 전체 `unit`: 32KiB 분할·역순·중복·데이터/ACK 누락 복구, 대기열 순서와 한 번만 처리, 잘못된 상대/라운드/순번/헤더/길이·손상 거절, 대기열/속도/버퍼 상한, 정확한 10초 마감·중복으로 마감 연장 금지·종료 해제. 재시도 조각을 일부만 보낸 중간에 도착한 이전 ACK도 정상 처리한다. 기존 그림그리기·자산·투표·갤러리 검사도 통과했다.
- `reliable-gallery`: **메모리 내** 독립 참가자 상태 3개(호스트 화면 포함)에 기존 PNG 3장, 참가자당 **891,234바이트 / 900개 이미지 패킷**을 전달했다. 제어 메시지 **15개 / 생성한 제어 패킷 93개**에서 데이터 15개와 ACK 15개를 의도적으로 누락했다. 각 동작은 한 번만 실행됐고 세 결과가 모두 **1/2/0표**로 일치했다. 대기열·수신 버퍼도 비워졌다. 93개에는 의도적으로 누락한 패킷도 포함한다.
- `control-loopback`: 같은 프로세스에서 실제 **로컬 UDP 소켓 두 개**로 임의 본문 **32,768바이트**를 보냈다. 첫 데이터와 첫 ACK를 하나씩 누락해도 본문이 일치했고 **한 번만 전달**, 송신 측 ACK 완료를 확인했다. 실제 송신 45패킷, 해당 실행 약 0.99초였다. 성능 기준이나 인터넷/다른 PC 검증 결과가 아니다.
- WPF Release 빌드: **경고 0 / 오류 0**.
- `scripts/check-eos-setup.ps1`: `config/eos.local.json` 부재로 종료 코드 **2**, EOS 준비 전이다.

원시 결과는 Git 제외 경로인 `outputs/multiplayer/reliable-gallery-check.json`, `control-loopback-check.json`에 있다. 기존 PNG는 `outputs/scoring-removal/packaged-drawing/generated.png`, `generated-repeat.png`, `generated-revised.png`를 재사용했다. 새 복제본에서는 이 로컬 생성 결과를 별도로 준비해야 하며 작은 PNG를 만드는 `unit` 검사는 해당 파일이 필요 없다.
