# 갤러리 배포·수신 확인·투표 결과 동기화 — 2026-09-25

후속 작업: 2026-09-26 제어 메시지 분할·재전송·ACK와 대기열/속도 제한을 추가하고 갤러리 통합·로컬 UDP 검사를 통과했다. 아래는 9월 25일 기록이며 최신 전송 구현과 남은 EOS 연결 범위는 [제어 전송 보고서](CONTROL_TRANSPORT_REPORT.md)를 따른다.

4번 작업의 SDK 독립 코드를 확장했다. 방장이 모은 그림을 각 참가자가 별도로 복원하고, 전원 수신 확인 후 투표를 시작하며, 호스트의 투표 상태·확정 결과를 참가자별로 적용한다. **EOS SDK·접속 설정은 여전히 없고 실제 네트워크 연결은 구현 전**이다. WPF 화면 연결·여러 라운드 진행도 남아 있다.

## 변경 파일과 동작

- `src/AIrtist.Core/GalleryProtocol.cs`: 갤러리 목록·수신 완료·전송 중단·투표 상태 메시지, 제어 메시지 인코딩/디코딩, 호스트의 갤러리 보관·준비 확인. 메시지 종류·통신 버전·JSON 깊이와 최대 32KiB를 검사한다.
- `src/AIrtist.Core/MultiplayerRoundClient.cs`: 로비 어댑터가 확정해 준 방장·참가자·경기·라운드를 기준으로 그림과 상태를 받는다. PNG를 별도로 복원·검증하고 한 사람의 한 표 요청과 재전송, 결과 보존을 관리한다.
- `MultiplayerRoundHost.cs`: 수집 완료와 투표 사이에 **Distributing** 단계를 추가했다. `GalleryPackets`로 승인된 PNG를 제공하고 `AcknowledgeGallery`로 전원 준비를 확인한 뒤 투표 타이머를 만든다. `VotingState`는 수신자 본인의 선택만 포함한다.
- `MultiplayerProtocol.cs`: 준비 확인과 단계 버전 변경을 구분하기 위해 규칙 버전을 **multiplayer-round-v2**로 올렸다. 이미지 패킷 통신 형식은 버전 1 그대로다.
- `tests/AIrtist.Checks/GallerySyncChecks.cs`, `MultiplayerChecks.cs`, `Program.cs`: 독립적인 참가자 상태 3개를 사용하는 배포·집계 검사, 오류·지연·버퍼 해제 검사를 추가하고 기존 호스트 검사에 준비 확인을 연결했다.

`GalleryManifest`에는 고정 참가자·그림 ID/소유자·파일 길이/해시·전송 ID가 있다. 이미지 바이트는 제어 JSON에 넣지 않고 기존 최대 1,024바이트 이미지 패킷으로 보낸다. 수신자는 배정된 방장 출처와 경기·라운드·갤러리 버전, 소유자·전송 ID·파일 상한을 검사한 뒤에만 버퍼를 할당한다. 모든 그림의 해시와 PNG 디코딩이 성공해야 수신 완료 메시지를 만든다.

호스트는 이미 모든 그림을 보유하므로 자신을 준비 완료로 처리하고, 다른 고정 참가자의 확인을 기다린다. 갤러리 버전은 `submissionVersion + 1`, 투표 버전은 `+ 2`다. 갤러리 수정·이미지 교체는 허용하지 않는다. 준비 완료 신호만으로 악성 클라이언트가 실제 그림을 보았음을 증명하는 것은 아니다.

## 상태·타이머·결과 검증

- 갤러리 수신 대기 중에는 투표를 받지 않는다. 마지막 준비 확인이 도착한 시점부터 투표 60초 기본값이 시작된다. 수신 시간은 투표 시간에서 차감하지 않는다.
- 새 갤러리 대기 기본값은 **60초**, `MultiplayerRoundPolicy.GalleryDuration`에서 1초~5분으로 조정한다. 전원이 확인하지 않으면 **GalleryTimedOut으로 라운드를 중단하고 표·승자를 만들지 않는다.** 아직 미확정인 이탈/그림 부족 정책의 임시 처리다. 준비가 끝난 참가자에게도 중단 메시지를 전달할 수 있다.
- 후보가 0~1개면 투표 없이 기존 `InsufficientImages` 결과를 확정한다. 참가자는 목록과 필요한 그림 수신 후 이 결과를 적용한다.
- 중복 목록·패킷·준비 확인은 새 버퍼나 새 타이머를 만들지 않는다. 패킷 순서 변경을 처리하며 충돌·SHA 손상·비정상 PNG·수신 시간 초과 시 미완료 버퍼를 해제한다. 참가자당 PNG 예약/보관 상한은 16MiB이며 디코딩 복사본·비트맵·SDK 큐를 포함한 프로세스 메모리 상한은 아니다.
- 투표 메시지는 방장 출처·수신자·경기/라운드/갤러리·투표 버전·revision을 검사한다. 낮은 revision, 같은 revision의 내용 변경, 확정 결과 교체, 자기 그림 선택, 맞지 않는 득표 합계·대상/소유자·최다 득표자·미투표 인원을 거절한다. 실제 표의 진위는 호스트와 인증된 연결이 보장해야 하며 클라이언트 검사는 구조·일관성 검사다.
- 동일 revision의 재전송은 남은 시간을 늘리지 않는다. 로컬 표시 타이머는 단조 시계를 사용하고 최종 마감은 호스트가 판정한다. 투표 요청 전송 중에는 새 선택을 막고 같은 요청의 재전송만 허용한다.
- `MarkHostUnavailable`은 새 투표를 막고 수신 중 버퍼를 해제한다. **이미 수신해 확정한 결과와 완성 그림은 유지**한다. 실제 이탈 감지·호스트 이전·재접속은 아직 연결하지 않았다.

## 수행한 검사

2026-09-25 .NET 10.0.103에서 전체 `unit` 통과, WPF Release 빌드 **경고 0 / 오류 0**.

- 모의 호스트에 제출한 그림 3장을 **독립된 참가자 상태 3개**로 각각 배포했다. 호스트 화면을 나타내는 로컬 참가자 상태도 이 검사에 포함한다.
- 실제 기존 Tiny-SD PNG는 참가자당 **891,234바이트 / 900개 원본 패킷**, 3개 상태에 총 **2,700개 원본 패킷**이다. 역순 처리하고 각 패킷을 한 번 더 재전송했다. 세 참가자의 PNG 바이트가 원본과 같고 결과가 모두 **1/2/0표**로 일치했다.
- 마지막 준비 확인을 59.999초에 보내도 투표 60초가 온전히 주어진다. 준비 확인 재전송이 투표를 일찍 시작하거나 타이머를 초기화하지 않음을 확인했다.
- 위조 송신자·수신자·이전 라운드/버전/갤러리, 중복/알 수 없는 소유자, 파일/전체 메모리 초과, 손상 메시지·빠진 본문·다른 종류/버전·알 수 없는 JSON 항목·32KiB 초과를 거절했다.
- 낮은 revision, 같은 revision의 다른 집계, 불일치하는 최종 득표/최다 득표자/미투표 수, 확정 뒤 높은 revision으로 덮어쓰기를 거절했다. 외부에서 역직렬화한 목록을 수정해도 보관한 결과는 바뀌지 않았다.
- 충돌하는 패킷·해시는 맞지만 PNG가 아닌 데이터·누락 후 시간 초과·중단·연결 상실 신호에서 버퍼와 투표 가능 상태를 확인했다. 후보 0/1개 결과 전달, 자기 표 거절, 요청 중복, 연결 상실 후 확정 결과 보존을 검사했다.

재현:


## 남은 연결과 현재 실행 파일

검사는 **메모리 안의 바이트 메시지 전달**이다. EOS·소켓·다른 PC·다른 회선·실제 이탈/재접속 검사와 다르다. 제어 메시지 최대 32KiB는 EOS 단일 패킷 크기가 아니며, 실제 어댑터가 크기 제한을 먼저 적용하고 별도 분할·재조립/재전송·송신 큐 제어를 해야 한다. 중단·최종 결과 등 제어 메시지의 수신 확인과 재전송, 준비 완료 후 방장 응답이 끊긴 경우의 연결 시간 초과도 어댑터에서 연결해야 한다.

다음은 [EOS SDK·프로젝트 설정 준비](EOS_SETUP.md) 후 기기 ID 인증·방 생성/참가·P2P 어댑터와 이번 처리의 연결이다. 여러 라운드 진행·온라인 UI·실제 여러 PC 검사도 남아 있다.

`testbuild/AIrtist.exe`는 기존 그림그리기·투표 미리보기 패키지 그대로다. 마지막 패키지 실측 922,301,469바이트 / 439개 파일이며 이번 소스를 새 EXE로 배포한 결과가 아니다. 이번에는 빌드와 Core 검사를 수행했고 WPF 실행 화면·GPU 생성·설치 용량을 다시 측정하지 않았다.
